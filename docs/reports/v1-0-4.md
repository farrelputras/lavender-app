## Decisions owed before dispatch

The release plan left four things to Lead. Resolving them here so the briefs are unambiguous. **All four
want Farrel's call; each is marked with what I recommend and why.**

### D-0 · There is no implementation plan, and I recommend not writing one yet `[by-agent]`

`docs/releases/v1-0-4.md` says the implementation plan is *"not yet written — owned by Lead."* v1.0.3 had
one before dispatch. **I am proposing we deliberately do not have one at dispatch time**, for a specific
reason rather than to save effort:

The central mechanism question of PRD-5 — *where does the text-scale clamp live so that it is genuinely
one decision (BR-8)?* — cannot be answered from the docs, and the obvious answers are likely wrong:

- **`Text.defaultProps.maxFontSizeMultiplier` is probably dead.** RN 0.83 / React 19 removed
  `defaultProps` support for function components, and RN's `Text` is a `forwardRef` function component.
  The most-cited global-clamp recipe on the internet would fail **silently** — no error, no clamp.
- **A clamp inside the wrapped `Text` component misses 37 raw-`Text` sites** (measured above).
- **Inline `fontSize` numbers** are plausible inside those 88 inline styles, which would defeat a
  token-level clamp too.

Planning a mechanism from that position is planning from belief. The project has an explicit lesson about
exactly this (v1.0.3, the `new Error(...)` mock: *"the test proves your belief about the library rather
than its behaviour"*).

**So: step ① is a read-only discovery pass, and Lead returns to Farrel with the mechanism before any code
is written.** The implementation plan gets written then, with facts in it. If Farrel would rather have a
plan document up front, say so and I will write one — but it will be conditional in exactly these places.

### D-1 · PRD-5 OQ-1 — the maximum supported text scale → **recommend `1.5`** `[by-agent, needs Farrel]`

The release plan resolved the *policy* (Mom is on MIUI "XL"; **cap high**, because under-capping shrinks
her text and reads as the app fighting her) but not the *number*.

**Recommendation: `MAX_FONT_SCALE = 1.5`.** Reasoning:

- MIUI's ladder is a labelled slider, not a number, and its mapping differs from stock Android's. I am
  not able to look up "XL" and get a trustworthy multiplier — and the release plan explicitly warns
  against doing exactly that.
- `1.5` sits above every value MIUI's slider is reported to reach, so **the clamp cannot be the thing
  that shrinks Mom's text.** That is the failure mode Farrel named as the expensive one.
- The cost is real and should be stated plainly: **the layouts must then survive 1.5×, not 1.3×.** That
  is more reflow work on 14 screens. I am recommending we pay it, because the alternative failure is
  discovered *on Mom's phone after publish*, and this release's only route to her device is the OTA
  itself.
- `1.3` was PRD-5's working assumption. If Farrel prefers it, that is a defensible call — but it should
  be made knowing it may sit *below* her actual setting.

**Companion recommendation — make this measurable instead of guessed** `[by-agent]`:
Beranda already renders a version footer (`app/config/release.ts`). Add **one line** to it showing the
device's reported `fontScale` and bottom inset. Cost: a few lines, zero risk, ships in the same OTA.
Benefit: Mom's next screenshot *tells us her real number* and simultaneously proves the inset is being
read — instead of us inferring both from whether the layout "looks fine". Remove it in the next release.

**Farrel's call on both.** If the footer line is unwanted, the cap stands on the cap-high argument alone.

### D-2 · The doubled-offset trap, named before it is built `[by-agent]`

PRD-4's constraints warn against "a doubled offset where a tab bar is also present" without saying where
it comes from. It comes from here, and both developers need it stated:

- Screens **inside the bottom tab navigator** (Beranda, Rental, Hutang, User) sit above a tab bar that —
  per PRD-4's Product-verified scoping note — **already accounts for the system inset.** Their scroll
  content must pad by **tab-bar height**, and adding `insets.bottom` on top of that double-counts.
- Screens **outside the tabs** (the *Sewa Baru* stack, the form screens, the detail screens) have no tab
  bar. They pad by the **raw `insets.bottom`**.

These are two different numbers and using one for both is the defect, pointed either way (dead band under
the tab bar, or *Simpan Rental* still covered). **BR-4 requires this be resolved once, in a shared
primitive — not decided per screen.** The mechanism (`useBottomTabBarHeight()` vs. a custom hook vs.
something the discovery pass finds already present) is the developer's call; **that it is one shared
decision is not.**

### D-3 · Who performs the enumerated visual audit, and on what `[by-agent, needs Farrel]`

This is the part of v1.0.4 I am least able to plan around, and I would rather say so than paper over it.

Almost every acceptance criterion in both PRDs is **visual and device-conditional**. Jest can prove a
handful of things honestly (below), and nothing else:

| Provable in Jest | Not provable in Jest |
|---|---|
| The shared hook returns 0 padding at `{bottom: 0}` and N at `{bottom: 48}` — **this is AC-5 / BR-5, the no-regression guard** | That a button is *visibly* clear of the nav bar |
| The clamp is applied by the shared primitive, at the chosen value | That a licence plate is not truncated |
| Screens render at a mocked `fontScale` without throwing | That a title and subtitle do not collide |
| Structural audit: no fixed-height container wrapping scalable text | Anything about how it *looks* |

So there must be a human visual pass over 14 screens × 2 conditions, and it must happen **before**
publish — because Mom's phone is only reachable *after* publish. Three options:

1. **Android emulator driven by `adb`** — recommended. Both conditions are settable:
   `adb shell settings put system font_scale 1.5` and forcing 3-button navigation via the
   `com.android.internal.systemui.navbar.threebutton` overlay. Reproduces Mom's configuration on a
   machine, repeatably, with screenshots attachable to the test report.
2. **Farrel's own device**, temporarily set to XL text + 3-button nav.
3. **Skip to Mom's phone.** Not acceptable — it makes her the first tester of 14 screens, and the release
   plan already commits to *"do not close the release on an emulator screenshot"*, which presumes there
   *was* one.

**Question for Farrel: is there a working Android emulator on this machine, and do you want the tester
briefed to drive it?** If not, the visual pass is yours and the plan should say so explicitly rather than
leaving it to be discovered at the gate. This is the single biggest schedule unknown in the release.

  tester proves it with `git diff --stat` — **zero changes under `app/services/`, zero under

### The contract I am brokering

Provisional — **confirmed or amended at the re-gate**, once discovery has told us what actually exists.
Locked from that point: **④ codes to it; ② implements it; neither changes it without coming back to me.**

```ts

/** Bottom space a screen must reserve. Resolves tab-bar vs. raw-inset itself (D-2). */

/** The one clamp value for the whole app (PRD-5 BR-8). One definition, one import site. */
```

Two invariants ride on this and are worth more than the names:

1. **`useBottomSpace()` returns `0` when the device reports no inset and there is no tab bar.** This is

   everyone else's.
2. **`MAX_FONT_SCALE` has exactly one definition site.** If ④ finds itself writing the number twice,
   BR-8 has failed and it must report rather than proceed.

## ⏸ RE-GATE — the clamp mechanism (PRD-5 BR-8)

Discovery returned three options and correctly declined to pick. **I am adding a fourth**, because the
three on the table all price in a cost I do not think this release has to pay.

### The cost driver, restated

Discovery's headline number is **~343 `<Text>` + 38 `<TextInput>` JSX tags**, and it concluded all three
options cost "~380 call sites". **That is true of Options 1 and 2. It is not intrinsic to the problem.**

It is true of **Option 1** (add `maxFontSizeMultiplier={MAX_FONT_SCALE}` to every tag) because the prop
goes on the tag. It is true of **Option 2** (route through Ignite's `components/Text.tsx`) because that
component has a *different API* — `preset` / `tx` / `text` / `weight` / `size` — so every tag has to be
rewritten to it, and its `TextField` sibling is not a drop-in for the 38 bespoke `TextInput`s at all
(F-2). Both numbers are real.

But the cost is a property of *those two designs*, not of the requirement.

### Option 4 — an API-identical passthrough, imported under the name `Text` `[by-agent, recommended]`

```ts
// app/components/AppText.tsx  — adds one default prop and nothing else
export const Text = forwardRef<RNText, TextProps>(
  ({ maxFontSizeMultiplier = MAX_FONT_SCALE, ...rest }, ref) =>
    <RNText ref={ref} maxFontSizeMultiplier={maxFontSizeMultiplier} {...rest} />
)
```

Because the component keeps **RN's exact props API and RN's exact name**, adopting it in a screen is an
**import-line change**, not a tag change:

```diff
- import { View, Text, StyleSheet, TextInput } from "react-native"
+ import { View, StyleSheet } from "react-native"
+ import { Text, TextInput } from "@/components/AppText"
```

**All 343 `<Text>` tags stay exactly as they are.** The migration surface is **~26 files, ~2 lines each** —
not 380 tags. Same for `TextInput` via a parallel thin passthrough (explicitly **not** Ignite's
`TextField`, which would be a BR-5 visual regression).

| Criterion | How Option 4 scores |
|---|---|
| Reaches every raw site? | **Yes** — the 22 screen-level and 14 form-component import sites all redirect |
| Reaches inline `fontSize`? | **Yes** — `maxFontSizeMultiplier` is orthogonal to styling. And per F-4 there is exactly **1** such site anyway |
| BR-8 durability | **Strong** — one definition, one file. The existing `no-restricted-imports` rule already bans raw `Text`/`TextInput` from `"react-native"`, so a new screen that does the wrong thing **fails lint today**, with no new rule to write |
| BR-5 (default size unchanged) | **Clean** — at scale 1.0 the prop does nothing. No style, no layout, no visual delta |
| Native dep | None |
| **Lint budget** | **Likely negative.** ~22 of the 159 real errors are `no-restricted-imports` in the 14 audit screens. Redirecting those imports **stops the rule firing** — this mechanism plausibly *pays down* debt #6 rather than drawing on it |

**Verify before committing — the three things that would kill it** (briefed to ④ as stop-and-report):

1. Any `<Text>`/`<TextInput>` reached by an aliased or namespace import (`import * as RN`), which an

2. Any site passing RN's `Text` as a *value* rather than rendering it — `Animated.createAnimatedComponent(Text)`,
   a `ref` typed as RN's `Text` instance, `Text.propTypes` — where a wrapper changes the type.
3. Whether nesting a wrapped `<Text>` inside a wrapped `<Text>` still inherits style as RN's does.

If any of those bites broadly, we fall back to Option 1 and the cost question reopens.

### Option 5, considered and rejected `[by-agent]`

Counter-scale the token font sizes: read `PixelRatio.getFontScale()` once and multiply every

## Agent / workflow improvements

- **A test's philosophy must be stated in its own name/comment**, or an implementation-derived assertion
  masquerades as a requirement gate. ⑤'s two fixed-height tests looked alike and behaved oppositely; the
  tell was buried in a comment. Tester briefs should require each structural assertion to declare whether
  it encodes a PRD requirement (defend) or documents current behavior (change-detector, expendable).
- **Write kill-thresholds in units that can't drift** — carried from ④'s "stop at 8 screens"; this session
  had no recurrence, but the lesson stands.
- **Resume-with-extended-scope beats a fresh dispatch for a tiny in-file follow-up** (⑧b) — context intact,
  same role, one edit, no re-briefing cost.
- **Persist any subagent artifact that exists only in a returned message immediately** — the checklist
  nearly evaporated once; the tester playbook should name its landing path.
