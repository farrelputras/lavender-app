### D-0 · No implementation plan yet — discovery first, and here is the specific reason `[by-agent]`

`docs/releases/v1-0-5.md` says the implementation plan is *"not yet written — owned by Lead."* I am
proposing we deliberately not have one at dispatch time, exactly as v1.0.4 did, and for a sharper reason
than v1.0.4 had.

**The release's largest line item is a test suite whose feasibility is unverified.** BR-12 requires
characterisation tests pinning `PengembalianScreen`'s current fuel-adjustment, return-total and auto-debt
behaviour, green **before anything moves**. But that screen has **zero** automated coverage (debt #15) and
is a 50KB component. So the suite is one of two completely different shapes:

| Shape | What it costs | What it requires |
|---|---|---|
| **Pure-function tests** — if the math lives in importable functions | Small, fast, precise | The math is *already* extracted |
| **Render-level tests** — mount the screen, drive inputs, assert displayed numbers + the payload handed to the connector | Large; needs connector, navigation, safe-area, image-picker and date-picker mocks | Nothing — but it may not be *possible* |

**And there is a circularity nobody has named yet.** If the math is inline in the component, making it
unit-testable means *extracting* it — which is product-code change on a fenced rental-math screen,
performed **before** the characterisation tests that are supposed to protect that screen exist. That is
the exact ordering BR-12 forbids. If render-level mounting also turns out infeasible, **the release as
scoped has no legal first step**, and that is a fact worth discovering in a read-only dispatch rather than
three dispatches deep.

So: **① is a read-only discovery pass that proves mountability by trying it** — a throwaway spike that
renders the screen and asserts one visible string. Evidence, not belief. This project's most reliable
habit is going back to the source (v1.0.4 C-1, and the `new Error(...)` mock lesson from v1.0.3); its most
expensive habit is reasoning about an artefact nobody opened (PRD-4 A-1). The implementation plan gets
written at the re-gate, with facts in it.

### D-1 · PRD-8 OQ-1 — the field box's fill → **`surface` `#f6faff`** `[by-agent]`

### D-2 · PRD-8 OQ-2 — the *Kembali* row: **box it, and keep the `inlineEditBtn`** `[by-agent]`

It is a Field under BR-4, so it wears the box. On the button, I am keeping both, deliberately:

1. **The box says "changeable"; it does not say "how".** A date/time is not typed — it opens a picker. The
   box makes the row look editable without telling Mom that tapping it does something. The explicit

2. **Debt #16 lives on this exact row.** It already renders a confident wrong default that has produced one

   confident wrong answer is not progress on this item."*
3. **Making the box itself tappable is a behaviour change**, not styling, and guard 1 draws the line at
   styling. So: box the row, keep the button, change no interaction.

> ⚠️ **Guard 1 goes into ⑤'s brief verbatim.** `returnedAt`'s `new Date()` seed is **not touched**. This is

### The contract I am brokering

**Provisional — confirmed or amended at the re-gate.** Locked from that point: **④ creates it; ④b and ⑤
consume it; nobody redeclares it without coming back to me.**

```ts
// app/components/form/FieldBox.tsx — the ONE definition site (BR-6, AC-6)

/**
 * The editable-field container. Wraps any input or picker row.
 * Boxed = Mom can change this. Plain = she can't. Two states only (BR-10/D-8).
 */
export function FieldBox(props: { children: ReactNode; style?: StyleProp<ViewStyle> }): JSX.Element
```

Five invariants, worth more than the name:

1. **Exactly one declaration** of the style set (border colour + fill + radius + `minHeight`) under `app/`.
   AC-6 is a source audit that fails if a second appears. **The trap is `RupiahInput`** — it declares
   treatment #2 today, and after this release it must **consume** the box, not carry its own copy. Same for
   every local style in `PengembalianScreen`. A consumer that needs a variant *composes*; it does not
   redeclare.
2. **`minHeight: 52`, never `height`.** BR-8, AC-2, and it closes the two live PRD-5 BR-1 violations at
   `PengembalianScreen:1203` / `:1221` — one of which is a **sub-48dp tap target on the money field**.
3. **Tokens only — no colour literal anywhere.** `colors.outline` for the border (retiring
   `outlineVariant` from field borders per BR-3), `colors.surface` for the fill (D-1),
   `borderRadius.default`. This is simultaneously BR-3/BR-6 compliance and the `no-color-literals` lint gate.
4. **It is a container, not an input.** It must wrap a `TextInput`, a date/time row, or a rupiah row without
   imposing an API on any of them — that is what keeps `Stepper` / `PhotoRow` / `SearchField` (Controls,
   BR-4) genuinely untouched instead of "refactored while we were in there".
5. **It carries its own doc comment** stating the convention, BR-4's three categories, the retired
   `outlineVariant`, the demoted tint, and the two known exceptions. BR-11 requires this **in the primitive
   itself** as well as in `docs/` — an undocumented convention decays back into ten treatments.
