### D-1 · OQ-1 — may Mom remove the last exit photo? → **No. Admin only.** `[by-Farrel]`

Lead recommended allowing an empty set; **Farrel overruled, 2026-07-20.** An exit-photo set may only
be emptied by **admin (Farrel)**. When ops tries to remove the last photo she gets an error telling
her to ask Farrel.

**The rule, stated precisely** `[by-agent]` — this needed sharpening, because the naive form has a bug:

> Reject when the **resulting** photo set is empty **AND** the **existing** set was non-empty **AND**
> the caller is not admin.

The `AND existing ≠ ∅` clause is not optional. The RPC rewrites `kondisi_keluar` **wholesale**, so an
ops edit of a rental that *already* has zero exit photos also sends `photos: []`. A gate written as
"ops may not send an empty set" would reject that — blocking a legitimate fuel correction on which Mom
removed nothing. The rule is *ops may not **reduce** a non-empty set to empty*; admin may always empty.

- **Server (RPC):** `RAISE` on violation — this is the enforceable copy of the rule (BR-1).
- **UI:** block the removal at the last photo for non-admin with a clear Indonesian message pointing
  at Farrel (e.g. *"Foto terakhir tidak bisa dihapus. Minta Farrel untuk menghapusnya."*), so Mom
  never round-trips to the server to learn she can't.

> ⚠️ **This contradicts PRD-1 and makes it stale.** **BR-5** ("Removing a photo … MUST NOT show her an
> error") and **AC-5** ("Removing a photo succeeds with **no** user-visible error") no longer describe
> intended behavior. The tester derives correctness from the PRD, so it is briefed on the amended rule
> explicitly — otherwise it would correctly report the intended behavior as a failure. **Product owes
> PRD-1 an amendment to BR-5/AC-5.** Logged as a follow-up, not a blocker.

### D-2 · OQ-2 — fuel-box `max` for the interactive control → **match the creation path** `[by-agent, needs verification]`

The correctness rule is *the edit control must produce values on the same scale as the control that
originally created `bensinKotak`* — otherwise editing silently rescales the baseline the return fuel
adjustment reads. The implementation plan records `DetailSewaScreen`'s local gauge at `max = 8` and
`PengembalianScreen`'s at none (debt #4). **Instruction to frontend: read the control that *creates*
`kondisiKeluar.bensinKotak` and use exactly its `max`; if it is not 8, stop and report rather than
choosing.** No gauge-unification refactor (explicitly out of scope, PRD-1 non-goals).

### D-3 · Debt #5 mechanism + on-timeout UX `[by-agent, needs confirmation]`

- **Mechanism:** a `fetch` wrapper on the Supabase client (`app/services/supabase/client.ts`) using
  `AbortController` + `setTimeout`, rejecting with a **real `Error`** carrying an Indonesian message
  (e.g. *"Tidak dapat terhubung ke server. Periksa koneksi Anda."*). Never the raw postgrest shape.
- **UX:** **no new UI.** BR-7's failure path already toasts the thrown message and stays in edit mode.
  A timeout simply becomes a normal failed save. This is the smallest possible blast radius.
- **⚠️ The real risk in #5 — timeout duration, not the wrapper.** This wrapper sits under *every*
  Supabase call including **storage photo uploads**. A tight timeout would turn a slow-but-succeeding
  multi-photo upload on mobile data into a spurious failure — which for Mom is **worse than the hang
  it replaces**, because it fails work that was actually going to complete. **Recommendation: 30s**,
  chosen to sit above a realistic slow-3G photo upload while still bounding the hang. If Farrel wants
  tighter, the honest alternative is a longer timeout for storage than for RPC/table calls — but that
  is a second mechanism and I would rather ship one number.

### Second-order finding from the contract reviewer — #5 is narrower than the debt register implies

## Discussion with PM and its resolution

**Consulted 2026-07-20** on Farrel's mid-execution directive that the RPC auth-gate hole ship *in*
v1.0.3 rather than deferring to its own release. PM was told the decision was made and asked to scope
it, not re-litigate it. It returned three things Lead had not seen.

### PM finding 1 — the escalation under-scoped the surface: **10 functions, not 6**

PM grepped the migrations tree rather than trusting the escalation. Beyond the six named
(`rpc_admin_delete_*` ×4, `rpc_update_payment`, `rpc_close_rental`) it found:

- **`rpc_delete_payment`** (`0014`) — sibling of `rpc_update_payment`, three lines away, identical
  idiom. Fixing one and not the other is not a defensible security release.
- **`rpc_create_rental`** (`0005`) · **`rpc_get_dashboard_summary`** (`0014`, redefining `0005`'s).
- **`recompute_rental_hutang`** (`0014:369`) — **the sharpest item, and previously unnamed by anyone.**
  `SECURITY DEFINER`, rewrites `jumlah_awal` on a hutang record, and has **no auth guard at all**. Its
  only protection is the comment `-- No GRANT — not callable directly by clients.` **That comment is
  false if F-2 holds**, since Postgres grants `EXECUTE` to `PUBLIC` by default. Unlike the other nine it
  has no NULL-logic bug — because it has no check. Where `0016`'s exposure is destructive-but-visible,
  this one is a **silent debt-amount rewrite**.

**Scoping rule PM proposed** (what stops this becoming "audit every RPC"): in scope = every function
that is **both** `SECURITY DEFINER` **and** reachable as a PostgREST RPC. Mechanically enumerable, has
an end, has an acceptance criterion. Out: RLS policies, views, table grants, storage policies, and any
body change beyond the guard line and grant/revoke.

### PM finding 2 — the release plan's **Rollback section is now wrong**

`docs/releases/v1-0-3.md` currently claims a JS-only OTA rollback is safe because the migration is
additive and inert. **True of PRD-1's migration; false of this one.** The auth migration *modifies
functions Mom uses daily* — create rental, close rental, payments, dashboard. OTA-republish does not
undo it. The release changes character from "one inert server change + reversible JS" to **an
irreversible-by-OTA change to live money paths.** The doc must be rewritten before ship.

### PM finding 3 — **the fix is riskier to the business than the vulnerability is**

The hole has existed since `0005` and needs deliberate intent against a two-user app. A botched
`REVOKE` breaks the business **immediately, for the only users, in the field, during handovers** — and
OTA rollback cannot fix it, because the damage is server-side the instant the push lands. The asymmetry
runs opposite to the one that got this escalated. Three failure modes: `REVOKE` too wide (strips
`authenticated` → whole app dead); polarity flip on `IS NOT TRUE` (a guard that never fired now
*always* fires → Mom cannot close rentals or record payments); silent body drift while "tidying".

This is **not** an argument against doing it — Farrel decided, and the decision is reasonable. It is
the argument for the preconditions below.

### Resolution `[by-agent]` — accepted in full, pending Farrel's approval of the widened scope

Lead accepts PM's scoping without modification. Notably PM **also** endorsed keeping debt #1 out (the
#5 message-degradation finding makes #1 look newly urgent precisely while someone is editing the error
path — that is scope creep wearing a good disguise), and recommended freezing v1.0.3's scope hard from
here: no CANCELLED status-chip fix, no lint-delta cleanup, no CLAUDE.md correction.

**Forward migration only.** PM's reasoning is a PM reason, not a SQL one, and Lead is recording it
because it is the best statement of this rule in the project so far: editing `0014`/`0015`/`0016` in
place would change *the repo's story* without changing *the database*, since `db push` skips applied
migrations. Every future reader would then believe the hole is closed while it is open — **worse than
not fixing it, because it destroys the ability to know.**

### New release gates PM specified (to be added to `docs/releases/v1-0-3.md`)

Ordering is **forced** by the fact that `docs/verification/` SQL cannot run until after the push:
`enumeration + body-invariance + math review` → **push** → `privilege + NULL-auth + live smoke`.
There is no arrangement in which the push is the last step.

- [ ] **Enumeration gate** (pre-push) — every `SECURITY DEFINER` function listed, each marked in-scope
      or out-**with a reason**. A function may be excluded, but **not un-mentioned.**
- [ ] **Privilege gate** (post-push) — for each: `has_function_privilege('anon', …)` = **false** AND
      `('authenticated', …)` = **true**. Both halves; the `authenticated`=true half is the
      anti-over-REVOKE check, and is exactly the omission that produced the vacuous script in §①c.
- [ ] **NULL-auth gate** (post-push) — unauthenticated call raises the **exact expected error**, not
      "an error appeared" (the §①c `EXCEPTION WHEN OTHERS` lesson, applied rather than relearned).
- [ ] **Body-invariance gate** (pre-push, review) — each replaced function's diff is confined to guard
      lines and grant/revoke. **No money logic moves inside a security migration.**
- [ ] **`rental-math-reviewer` re-sign** — non-negotiable; four of the ten are money paths. Its existing
      sign-off covered `rpc_update_rental` only.
- [ ] **Live positive-path smoke on the preview APK, by Farrel, as Mom's account (not admin)**,
      immediately post-push: create rental · close rental · add/edit/delete payment · load dashboard.
      **The only gate that proves Mom is not locked out** — SQL privilege checks can pass while the app
      is dead.

**Blocking precondition** `[by-agent, from PM]`: a **forward-rollback (restore-grants) migration must
be authored and reviewed *before* the push** — calmly, not at 11pm with Mom unable to close a rental.
This is what makes the irreversibility survivable.

## Bottlenecks

**1. The release doc's verification claims went stale silently, and nobody re-derived them until the end.**
This is the most expensive one, and it is not a scheduling problem. The Rollback section said an OTA
republish was a safe rollback. That was true of one additive migration. It became **false** the moment
the hardening migration was added — and it stayed wrong on paper through the entire execution, flagged
in the handoff as *"🔴 the Rollback section is WRONG"* and rewritten only just before the push. Had the
push gone badly at any point before that rewrite, the document an operator would have reached for
under pressure was actively misleading. **Each scope admission invalidated a claim nobody re-checked.**

**2. The gated push serialized everything downstream.** AC-4 and the server half of AC-6 could not be
closed before `db push`, and the push was correctly gated on Farrel being at a keyboard able to smoke
test within minutes. This is not a process defect — the gate is right — but it means a release of this
shape has a hard serialization point, and roughly a third of the acceptance criteria sat PENDING behind
it. Worth planning for rather than discovering.

**3. Test-run confusion cost a detour at the worst moment.** A full-suite run from the monorepo root
(instead of `apps/lavender-ops-mobile`) resolved a different config and swept in a stale
`.worktrees/feat-v1-0-1-phase-3/` tree, reporting a wall of failures across files nobody had touched —
immediately before a gated production push. It looked exactly like "the money fix broke everything."
The correct run was 32 suites / 174 green. **Any `jest` invocation here must pin its directory**;
recorded so the next session does not re-derive it.

**4. Review round-trips on the reviewer's own artifacts.** The `rental-math-reviewer` gate passed the
migration on the first pass (body invariance, ordering, rental math) but found real defects in the
*test and verification* work — including two that would have passed vacuously. Those were fixed and
re-verified before commit. Correct outcome, but it means the review gate's cost is paid twice: once on
the product change, once on the evidence for it.

**5. Documentation drift as a standing tax.** Three separate documents were found asserting things that
were no longer true: the Rollback section, the verification README's *"AUTHORED, NOT YET RUN"* status
lines, and the hardening migration's *"pre-existing since 0005"* note. None broke code. All three would
have misled the next reader on a safety-relevant question.

## Best practices applied

**1. Mutation-verified the guard test instead of trusting it.** The body-invariance test for
`rpc_close_rental` was checked by deliberately breaking the migration three ways and confirming each
was caught: reverting the auth guard (2 failures), a pure statement reorder (1), dropping the
`deleted_at` filter (3). The file was then restored and diffed byte-for-byte against a backup. This is
what caught that the **first version of the test was order-blind** — it used a set-difference diff, so
hoisting a statement (which changes the money) produced an *empty* diff and passed. A test asserting
"the body did not change" must be index-aligned, because in a procedural body **order is semantics**.

**2. The money fix went in its own migration.** Folding it into the hardening migration would have
destroyed that migration's body-invariance property — the very thing being reviewed — and made the
money change unreviewable and un-revertible on its own.

**3. Based the fix on the *hardened* body, not the original.** Because `CREATE OR REPLACE` restates the
whole function and the hardening migration also redefines `rpc_close_rental`, rebasing the money fix on
`0015` would have restored the filter while **silently reverting the auth fix** — the identical failure
mode to the original bug, pointed the other way. Ordering (`20260721…` sorting after `20260720…`) is
load-bearing and is documented in the file header as such.

**4. Verified the live database independently of the scripts that were supposed to verify it.** After
the push, a separate read-only query read the **deployed** function body out of `pg_proc` and checked
privileges via `has_function_privilege`. Different route, same properties. This caught nothing — but it
is what makes "the scripts passed" mean something, given the scripts were run section-by-section in a
web console where a helper that spoofs `auth.uid()` can survive.

**5. Sanity-checked a zero before reporting it as good news.** The damage audit returned
`completed_rentals: 0`. That is equally the signature of a silently broken query. It was confirmed
against raw row counts (`v_rentals` returned its row, so the join worked) before being reported.

**6. Honest gates.** The lint gate was **not** ticked. Recording a knowingly-accepted breach with a
reason is worth more than a green checkmark that means nothing.

**7. Fixed forward, never in place.** No applied migration was edited. The one edit to an *unapplied*
migration was comment-only, flagged explicitly to Farrel with an offer to revert.

**8. Corrected the reviewer where it was wrong.** PM reported 25 raw-throw sites; the actual count is
24. Verified before writing it into the register rather than propagating it.

## Agent / workflow improvements

### The scope freeze needs renaming, not reinforcing

The freeze was broken twice and both calls were right. That is not a discipline failure — it means the
process encoded the wrong noun. A freeze on *scope* asks "is this in the plan?" The question that
actually decided both cases was **"does shipping over this make us complicit in it?"**

The asymmetry that matters, and it is sharp: both admissions were **defects in already-shipped code,
discovered by this release's own work**. Debt #1 was **known debt that merely looked urgent because the
release was standing next to it** — and Farrel refused it. Proposed rule:

> **The freeze binds new value, not discovered harm.**
>
> **Frozen (decline and log):** anything that *adds* — capability, polish, quality, or paydown of
> **already-known** debt. Known debt does not become admissible by becoming convenient.
>
> **Admissible by explicit decision**, all four required: (1) **live harm** in production now, with a
> money / access / data-integrity consequence; (2) **discovered by this release's own work**, not
> imported from a list; (3) **bounded and separable**, shippable as its own migration/commit/test so
> existing review gates stay valid; (4) **passes its own review**, not the release's.
>
> **Fails any one → defer, log, and protect the user in the meantime.** A deferred live defect with no
> user-facing mitigation is not a deferral — it is a decision to let it keep happening quietly.
>
> **Ceiling: two admissions.** A third means the release is wrong, not the scope — cut the original
> feature scope and re-plan. v1.0.3 sat at exactly two and was visibly straining.

### The rule that outranks the scope rule

> **An admission is not complete until the release doc's *Delivery model* and *Rollback* sections have
> been re-derived — before the push, not after.**

Scope creep here is not a schedule risk (the schedule is Farrel). It is a **verifiability** risk: the
release's claims about how it can be undone go stale while everyone is looking at the code. That is
what "frozen" was really protecting.

### What the agent system got right

- **The pre-execution approval gate worked exactly as designed.** `/lead` halted for Farrel before
  dispatching, and both scope decisions were made by a human with the tradeoff written down.
- **Role separation caught what a single pass would not.** `developer-backend` found the `deleted_at`
  omission and **correctly refused to fix it inside a security migration**; `rental-math-reviewer` then
  corrected the *provenance* (regression, not legacy debt), and that correction is what changed the
  decision. Neither role alone gets there.
- **Consulting `product` and `pm` at close-out surfaced the highest-value item in the release.** PM
  asked whether corrupted data was already sitting in the database — a question nobody had raised, and
  the only one that could have meant real customers were owed money. It took one read-only query to
  answer, and the answer (none) is now on the record instead of being an unexamined assumption.

### What to change next time

1. **Re-derive the rollback story at every scope admission**, as a checklist item, not a habit.
2. **Pin the working directory in every test command.** See Bottlenecks #3.
3. **Treat "verification script authored" and "verification script run" as different states**, and make
   the README's status line part of the release gate — two of three scripts still read *"AUTHORED, NOT
   YET RUN"* after they had been run and passed.
4. **Give the reviewer roles the evidence, not just the code.** The most valuable findings this release
   were in the *tests and verification scripts*, not the product change — including two that would have
   passed vacuously. That is where review time paid best.
