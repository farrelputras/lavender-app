## Item 2 — "Kembali ke Beranda" on completed rental

**Problem.** After a return, mom lands on `RentalDetailScreen` for the now-`COMPLETED`
rental. That screen renders a sticky bottom bar **only** when `status === "ACTIVE"` (the
"Proses Pengembalian" CTA). A completed rental has no bottom bar — the only way back is
the top-left arrow, which mom doesn't reliably notice.

**Design.** Render a mirror sticky bottom bar for the completed state containing a
full-width **"Kembali ke Beranda"** button that calls the existing `handleBack()`
(`navigation.reset({ index: 0, routes: [{ name: "MainTabs" }] })`). The top-left arrow is
unchanged. Style mirrors the existing `bottomBar` / active CTA.

**Files.** `app/screens/RentalDetailScreen.tsx`.

## Item 3a — Don't pre-fill Jumlah Pembayaran

**Problem.** The "Tambah Pembayaran" sheet pre-fills the amount with the outstanding
balance (`defaultAmount={sisa}`), so mom can rubber-stamp a wrong figure without reading
it.

**Design.** Drop `defaultAmount` on the **add** path at every caller (`RentalDetailScreen`,
and the Pengembalian / HutangDetail sheet openers — verify each). `PembayaranSheet`
already resets `rawDigits` to `""` when no `editingPayment` and no `defaultAmount`, so the
field opens empty and mom must type the amount.

**Edit path is unchanged** — an edited payment must show its existing amount; that is the
record, not a pre-fill.

**Files.** `app/screens/RentalDetailScreen.tsx`, `app/screens/PengembalianScreen.tsx`,
`app/screens/HutangDetailScreen.tsx` (whichever open the add sheet — confirm during
implementation).

## Item 3b — Tarif & Total: read-only suggestion, no pre-fill

**Problem.** `DetailSewaScreen` computes `defaultTarif = composeTarif(vehicle, hari, jam)`
and (a) shows it as the field's numeric **placeholder**, (b) shows a "Tarif default: Rp X"
hint, and (c) **silently falls back** to it when the field is empty. Mom can submit the
computed number without ever consciously entering it.

**Decision (from brainstorm).** Keep the computed value **visible but read-only** as a
suggestion; mom types the tarif herself every time. `composeTarif` still runs — it just
informs rather than fills.

**Design.**
- Remove the numeric placeholder on the tarif input → neutral prompt (e.g. "Masukkan
  tarif"), not the number.
- Remove the silent fallback: `tarifValue = tarifRaw ? parseRupiahInput(tarifRaw) : 0`
  (was `: defaultTarif`). An empty field is invalid; the existing guard "Tarif harus lebih
  dari 0" already blocks submit.
- Keep the computed value shown as a **read-only** line, relabeled `Saran tarif: Rp X`
  (was "Tarif default:"). Non-tappable — it does not fill the field.
- Total already derives from `tarifValue`; with `tarifValue = 0` until entry, Total reads
  Rp 0 until mom types the tarif — so no pre-filled total, for free.
- Remove any auto-seed of the tarif field (the `tarifSeeded` ref effect) so the field
  never populates with the number.

**Files.** `app/screens/DetailSewaScreen.tsx`.

## Item 4 — Pinch-to-zoom photo viewer

**Problem.** Photos (KTP/KTM/profil, vehicle Kondisi Keluar/Kembali) render as 120px
thumbnails with no way to enlarge. `PhotoThumb` has no tap handler on the image — mom
can't read a plate number or KTP text.

**Design.** New shared component `PhotoViewer` — a full-screen `Modal` showing one image
with **pinch-to-zoom + pan + double-tap-to-zoom** and a close (✕), built on the
already-installed `react-native-gesture-handler` + `react-native-reanimated` (OTA-safe; no
native rebuild). Add an optional `onPress` to `PhotoThumb` (and thread it through
`PhotoRow`); tapping a thumb opens the viewer for that image.

Wire the tap on:
- `RentalDetailScreen` — Kondisi Keluar / Kondisi Kembali photos.
- `UserDetailScreen` — KTP / KTM / profil photos.

**Files.** new `app/components/form/PhotoViewer.tsx`; `app/components/form/PhotoRow.tsx`
and `app/components/form/_PhotoThumb.tsx` (add `onPress`); `app/screens/RentalDetailScreen.tsx`,
`app/screens/UserDetailScreen.tsx` (wire). Component test for `PhotoViewer` open/close.

## Item 6 — Admin hard-delete across entities

**Problem.** There is no way to permanently remove a mistaken or test record. Only
`softDeleteUser` / `softDeleteVehicle` exist; rentals, payments, charges, and hutang were
"never deleted in v1" (per `0003_tables.sql`). Farrel (admin) needs an emergency
hard-delete.

**Key schema fact.** No foreign key declares `ON DELETE CASCADE`
(`rentals.user_id`, `rentals.vehicle_id`, `charges.rental_id`, `payments.rental_id`,
`payments.hutang_id`, `hutang.user_id`, `hutang.rental_id`). A raw `DELETE` is therefore
blocked whenever dependents exist — each RPC must walk the graph in the right order.

**Authorization.** Reuse the established admin gate inside a `SECURITY DEFINER` RPC:
`auth.uid() = (SELECT user_id FROM app_config WHERE role = 'admin')`. Because the function
runs as definer and bypasses RLS, no new `DELETE` RLS policies are required — the gate is
the whole authorization story (mirrors the Stage-C payment RPCs).

> ### ⚠️ CORRECTION (2026-07-12, during implementation)
>
> **"No new `DELETE` RLS policies are required" was wrong** — true for the *tables*, false for
> *storage*.
>
> The RPCs run as definer and bypass RLS, so table deletes need no policy. But **photo cleanup
> does not happen inside the RPC** — `removePaths()` is a *client-side* call made by the
> connector after the RPC returns (see "Connectors" below, which specifies exactly that
> ordering). A client-side call is fully subject to RLS.
>
> `storage.objects` had only `operators_insert_photos` (INSERT) and `operators_select_photos`
> (SELECT); `0006_rls.sql` states outright that *"Hard DELETE is denied everywhere (no DELETE
> policies created)"*. So every `removePaths()` call was **blocked by RLS and its error swallowed**
> by the deliberate best-effort `.catch(() => {})`. Hard-deleting a customer erased their row but
> left their **KTP/KTM ID scans in the bucket permanently** — a privacy failure, silent by
> construction.
>
> Fixed by **migration `0017_storage_delete_policy.sql`**: `FOR DELETE` on `storage.objects`,
> scoped to the `rental-photos` bucket, granted to the **admin role only** — mirroring the RPC
> gate, and leaving mom's `ops` role unable to delete any file.
>
> **Lesson for future designs:** "`SECURITY DEFINER` bypasses RLS" only covers what runs *inside*
> the function. Any client-side step in the same workflow — storage, a follow-up table write —
> is still an RLS subject and needs its own policy.

**Delete semantics** — cascade *owned* data, protect *referenced* data:

| RPC | Behavior |
|-----|----------|
| `rpc_admin_delete_rental(p_rental_id uuid)` | Cascade owned children in FK order: hard-`DELETE` rental `payments` → linked `hutang` (+ its payments) → `charges` → the `rental`. If the rental was `ACTIVE`, release the vehicle (`status = 'TERSEDIA'`). |
| `rpc_admin_delete_hutang(p_hutang_id uuid)` | Delete its `payments`, then the `hutang`. |
| `rpc_admin_delete_user(p_user_id uuid)` | **Block if referenced** — raise if any `rentals` or `hutang` reference the user; else `DELETE` the user. |
| `rpc_admin_delete_vehicle(p_vehicle_id uuid)` | **Block if referenced** — raise if any `rentals` reference the vehicle; else `DELETE` the vehicle. |

Rationale: rental/hutang children (payments, charges, auto-hutang) have no meaning apart
from their parent, so they cascade. A user or vehicle is *referenced* by history;
cascading one would silently wipe an entire rental/debt trail on a single misclick, so
those **block** — the admin must delete the referencing rentals first. (Confirmed with
Farrel: block-if-referenced, not full-cascade.)

**Migration.** `supabase/migrations/0016_admin_hard_delete.sql` — the four RPCs above,
each `SECURITY DEFINER`, `SET search_path = public`, admin-gated, with
`GRANT EXECUTE ... TO authenticated`.

**Connectors** (locked, async — `app/services/rentals/index.ts`):
- `hardDeleteRental(rentalId: string): Promise<void>`
- `hardDeleteHutang(hutangId: string): Promise<void>`
- `hardDeleteUser(userId: string): Promise<void>`
- `hardDeleteVehicle(vehicleId: string): Promise<void>`

Each calls its RPC, then cleans up **storage photos it owns** after the RPC succeeds
(rental Kondisi Keluar/Kembali photos; user KTP/KTM/profil) using the existing photo
bucket/path convention. Ordering: RPC first, then storage removal — a storage failure
leaves orphaned files (tolerable for an admin tool) rather than a deleted file with a live
row. The block-if-referenced RPCs (user/vehicle) surface their rejection as a thrown
error the UI shows as a toast ("Tidak bisa dihapus: masih ada rental/hutang terkait").

> ### ⚠️ CORRECTION (2026-07-12, during implementation)
>
> **"Surface their rejection as a thrown error the UI shows"** did not work as written, because
> of an assumption about what `supabase.rpc()` throws.
>
> The client is not configured with `.throwOnError()`, so postgrest returns its `error` as a
> **plain object** (`{message, details, hint, code}`), *not* an `Error` instance. The connectors
> did `throw error`, and the screens then did `e instanceof Error ? e.message : "<fallback>"` —
> which is **always false**. The Postgres message was therefore *always* discarded, and the
> operator only ever saw the generic fallback.
>
> This mattered most exactly where the design cared most: `rpc_admin_delete_user` is
> block-if-referenced, so any customer *with* rental history takes the error path. The admin would
> tap "Hapus Permanen", get "Coba lagi", learn nothing about why, and reasonably conclude the
> button was broken.
>
> Fixed at the connector layer — the four `hardDelete*` connectors now
> `throw new Error(error.message || "…")`, which repairs all three screens at once and keeps the
> locked signatures intact. The unit tests had concealed the bug by mocking the failure as
> `error: new Error(...)` — a shape supabase never actually produces; they now mock the real
> plain-object shape and fail if the connector regresses.
>
> **Lesson for future designs:** don't assume the shape of a library's error. Mocking a
> dependency encodes your *belief* about it — if that belief is wrong, the test proves the belief,
> not the behavior, and it goes green over a real bug.
>
> See also **Known technical debt** in `docs/feedback-and-improvements.md`: the ~24 *other*
> `throw error` sites in the connector layer still have this flaw.

**UI.** An admin-only (`isAdmin` from `useSession`) destructive action on each entity's
detail surface — `RentalDetailScreen`, `HutangDetailScreen`, `UserDetailScreen`, and the
vehicle detail/edit surface — behind a confirmation `Alert` (destructive style). Whole-history
targets (user/vehicle) get an extra-explicit confirmation naming the entity. On success:
toast + navigate back / refresh the list.

> **As shipped (2026-07-12):** the **vehicle UI was dropped** — there is no vehicle detail/edit
> surface in the app (`KendaraanScreen.tsx` is a placeholder stub with no route in
> `AppStackParamList`). `rpc_admin_delete_vehicle` + `hardDeleteVehicle` ship with tests, so it is
> a one-screen wire-up whenever that screen is built. The other three shipped as designed.
>
> Two safety hardenings were added beyond this design: **all three** confirmations now name the
> record they will destroy (the design only required it for user/vehicle — but a rental cascade is
> just as irreversible), and `UserDetailScreen`'s permanent-delete uses a **filled** destructive
> style, because it sits directly beside the reversible soft-delete and reusing the same outlined
> style made the two nearly indistinguishable.

**Files.** `supabase/migrations/0016_admin_hard_delete.sql`; `app/services/rentals/index.ts`
(4 connectors); the four detail screens (admin action + confirmation). SQL-behavior notes
and translator/connector tests as applicable.
