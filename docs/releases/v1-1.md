# v1.1 — Replace the Supabase client with a separate backend service

- **Status:** open — **undesigned, undated, and not committed to.**
- **Origin:** carried over from `docs/feedback-and-improvements.md` (§ v1.1) when the release docs
  were split on 2026-07-12. Unchanged in substance; it has never been discussed in depth.

## The idea

Today the app talks to Supabase directly via `@supabase/supabase-js` from the device. Replace that
with a backend service of our own that the app calls instead.

## Why this is not scheduled

This is a **major architectural change** and needs to be argued for on its merits before any work
starts. It would touch:

- The **connector layer** (`app/services/rentals/`) — though *only* the connector layer, if the
  contract rules in `docs/02` §3 have held. That is precisely the migration the architecture was
  designed to make cheap, and it is the strongest argument that this is *doable*. It is not an
  argument that it is *worth doing*.
- **Auth** — `useSession`, role gating (`ops` / `admin`), token storage in `expo-secure-store`.
- **RLS** — currently the security boundary. A bespoke backend would have to re-implement every
  policy in application code, and would be trusted to. Migrations `0006`, `0016`, `0017` are the
  current shape of that boundary.
- **Storage** — photo upload and (admin-only) deletion.
- **Ops** — something must now be deployed, monitored, patched, and paid for. Today there is no
  server to run.

## Questions to answer before designing anything

1. **What problem does this actually solve?** Name it concretely. "Supabase is a dependency" is not
   a problem. A specific limit we have hit, or a cost we are paying, is.
2. What breaks or gets harder if we *don't* do it?
3. Who operates the service? This is a two-person internal tool (mom + Farrel) for a small rental
   business. Introducing a server we must keep alive is a real, ongoing cost against a currently
   zero-ops setup.
4. Does re-implementing RLS in application code make the system **more** or **less** secure, honestly?
5. Is there a smaller change that gets most of the benefit — e.g. Supabase Edge Functions for the
   handful of operations that genuinely want server-side logic?

## Recommendation

Do not schedule this until question 1 has a concrete answer. If a real motivating problem shows up,
run `superpowers:brainstorming` on it then — and be genuinely willing to conclude that the answer is
"keep Supabase".
