## Why these two ship together

They were written as separate PRDs because they have **different root causes** and must not be merged
as requirements. They ship in **one release** because they share everything else that matters to
delivery:

- Same files. Both are layout changes across the same screens.
- Same delivery model. Both are JS-only, OTA-only, no server surface.
- **Same verification event, and it needs Mom.** PRD-4 AC-8 and PRD-5 AC-8 both require confirmation
  on *her* phone. PRD-5's own edge-behavior section names "large text *and* 3-button nav" as the
  configuration that must be verified — that is one device in one session, not two.
- Splitting means sweeping every screen twice and spending Mom's attention twice, with PRD-5 landing
  on a vertical-space budget PRD-4 has already changed underneath it.

**PRD-4 goes first** for that last reason: it changes how much room every screen has. Reflowing text
(PRD-5) against a budget that is about to move is work done twice.

## Scope — in / cut

**Nothing is cut.** All of PRD-4 and all of PRD-5 ship. Both PRDs are app-wide by construction
(PRD-4 BR-4, PRD-5 BR-7/G5), and cutting either back to "the four screens Mom photographed" was
explicitly refused by Product — correctly: the un-audited screens carry the identical latent defect,
and the next report would be the same report.

### The one requirement this release cannot fully meet: PRD-4 BR-4

PRD-4 BR-4 says the fix lives in the shared bottom-bar primitive so every screen inherits it, and that
"a per-screen patch list is not an acceptable outcome." **On the current codebase that is not
achievable without opening the rental-math screens.** Verified 2026-07-22:

- `components/form/BottomActionBar.tsx` is imported by **2** screens: `HutangFormScreen`,
  `UserFormScreen`.
- **3 screens roll their own** bottom bar: `DetailSewaScreen.tsx:998`, `PengembalianScreen.tsx:977`,
  `RentalDetailScreen.tsx:868` and `:884`.
- **The blocked button is in a local bar.** *Simpan Rental* — PRD-4 **AC-1**, the flagship criterion
  and the single highest-consequence control in the app — is in `DetailSewaScreen`'s local bar. That
  file is tariff composition, fenced by debt **#4**.
- No screen declares `safeAreaEdges` at all (only `ErrorScreen/ErrorDetails.tsx`). PRD-4's constraints
  section assumes screens declare a top edge; they declare none.

**Decision (Farrel, 2026-07-22): layout patch only — no component swap.** The three local bars get the
same inset applied locally. They are **not** migrated onto `BottomActionBar`.

- **Why:** migrating them *is* debt #4's refactor, inside `DetailSewaScreen` (tariff) and
  `PengembalianScreen` (fuel adjustment + auto-debt). Debt #4 requires that to have its own release,
  characterisation tests on the math first, and a `rental-math-reviewer` pass. A P0 spacing fix must
  not become the vehicle for it.
- **What this costs:** the duplication in debt #4 grows — the local bars now carry inset logic too.
  **Record it as an addendum to #4 on ship.** It is accepted knowingly, not overlooked.
- **What BR-4 still binds:** the shared `BottomActionBar` and the shared screen scaffolding **must**
  be fixed properly, so a *new* screen inherits correct behavior (PRD-4 AC-7). The waiver covers only
  the three existing local bars.

## Sequencing & guards

1. **PRD-4, then PRD-5.** Space before text.
2. **Do not swap components in the three local bars.** Spacing only. No change to any calculation,
   connector, or value in `DetailSewaScreen` / `PengembalianScreen` (PRD-5 constraint: "presentation
   only").
3. **Do not run `eslint --fix` or `prettier --write` across the repo.** This release touches nearly
   every screen file, which makes the temptation maximal and the damage maximal — debt **#6a** says a
   CRLF renormalization must be its own dedicated whitespace-only commit, reviewable in isolation.
   Folding it into an app-wide layout diff would make both unreviewable.
4. **No new native dependency.** If the chosen approach reaches for one (an edge-to-edge or
   immersive-mode package, say), it stops being OTA-only and breaks PRD-4 AC-9 / PRD-5 AC-10 — that is
   an APK release and a different plan. **Escalate rather than absorb it.**
5. **`KendaraanScreen` is out of the PRD-5 AC-5 audit surface.** It is unreachable dead code
   (commented out of `MainNavigator`) — debt **#3**. Note it as excluded in the test report rather
   than auditing or deleting it; deleting it is a product decision about vehicle management, not this
   release's call.
6. **Mom's phone is the last gate, and it happens after publish** — see Release gates.

## Rollback

**Fully OTA-revertible.** No migration, no Edge Function, no schema or privilege change — nothing
this release does survives republishing the previous update group. Find it with
`eas update:list --branch preview` and republish.

This is worth stating plainly because it is *not* how v1.0.3 rolled back: that release applied three
migrations, two of which an OTA republish could not touch. Here there is exactly one failure mode and
exactly one response.

**Trigger:** Mom reports anything worse than before — controls newly unreachable, text smaller than
she set it, a layout that breaks on her device. Republish first, diagnose after. She is the only
operator, and a broken layout blocks the whole business day.
