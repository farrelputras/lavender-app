# v1.0.2 — Polish & Honesty

- **Status:** ✅ **shipped OTA 2026-07-15** (channel `preview`, runtime `1.0.0`, update group `0ce732a0-9d6d-410b-b292-d4e1b498c908`)
- **Ships as:** OTA only (channel `preview`). No migration, no native dep, no APK, no `version` bump.
- **Theme:** *polish + honesty.* Fix what looks wrong, remove what lies, and tell mom which
  version she is running.
- **Predecessor:** `docs/feedback-and-improvements.md` § v1.0.1
- **Successor:** `docs/releases/v1-0-3.md` (active-rental editing — split out of item 3)

## Why this release has no database surface

Every item below is JS/asset only. That is deliberate: it keeps the release cheap to verify and
cheap to roll back. The one candidate that *would* have added a migration — editing an active
rental — was split out into v1.0.3 so it can get its own design pass, because it moves the fuel
baseline the return calculation depends on (`docs/02` §6).

Do not let a migration creep into this release. If one becomes necessary, that item belongs in
v1.0.3.

## 1. Adjust some text sizes

- **Status:** open — **carried over from v1.0.1** (deferred twice; still blocked)
- **Blocked on:** mom's specific "too small / too large" spots. Not yet gathered.
- **Ships in v1.0.2:** nothing. This entry exists to keep the item alive, not to schedule work.

### Finding recorded 2026-07-12 (do not rediscover this)

`allowFontScaling` appears **nowhere** in the codebase. React Native's default for `<Text>` is
`allowFontScaling={true}`, so **Android's system font-size slider already resizes the app's text
today.** Mom may simply not know the setting exists.

That reframes the item. The open question is probably not *"what sizes should we pick?"* but:

1. Does mom know about **Settings → Display → Font size**? Showing her may resolve the whole item
   without a line of code, and it gives her a dial we don't have to guess at.
2. **Does the app survive her using it?** `app/theme/tokens.ts` pairs every tier with a hard-coded
   `lineHeight` —

   | tier | size / lineHeight |
   |---|---|
   | `labelMd` | 14 / 18 ← tightest, clips first |
   | `labelLg` | 16 / 20 |
   | `bodyMd` | 16 / 24 |
   | `bodyLg` | 18 / 28 |
   | `headlineSm` | 20 / 28 |

   — which is exactly the pattern that clips and overlaps once the OS scales text up. Likely
   breakage: `numberOfLines={1}` truncation on card titles, `BottomActionBar` height,
   `StatusPill` overflow.

**Suggested next step when this unblocks:** run the app at Android font scale 1.15× / 1.3× / 1.5×
and fix what breaks, rather than hand-tuning `tokens.ts` numbers against a guess.

## 2. Minor UI fixes

- **Status:** open — closed list, ready to execute
- **Source:** partly mom/Farrel observation, partly a read-only audit of all 15 screens (2026-07-12)

### 2.1 `HutangScreen` chevron overlaps the status pill

`app/screens/HutangScreen.tsx:216`

```ts
chevron: { position: "absolute", right: spacing.md, top: spacing.md },
```

This pins the chevron to the card's **top-right** — which is exactly where `cardHeader` already
renders the "Dari rental" / "Manual" `StatusPill`. They collide.

Every other list in the app uses an **inline flex** chevron as the last child of a row:
`UserScreen.tsx:90`, `PilihUserScreen.tsx:102`, `BerandaScreen.tsx:197`.

**Fix:** drop the absolute positioning; render the chevron inline (vertically centred against the
card footer, matching the other lists). Delete the `chevron` style entry.

### 2.2 `BerandaScreen` notification bell is dead

`app/screens/BerandaScreen.tsx:105`

```tsx
<MaterialIcons name="notifications" size={24} color={colors.onSurfaceVariant} />
```

A bare icon — no `onPress`, no `TouchableOpacity` wrapper. It looks tappable and is not. The app
has no notifications feature and none is planned.

**Fix:** delete it. (Decided 2026-07-12 — not deferred, not wired up.)

### 2.3 `SearchField` is not adopted everywhere

Stage B introduced a shared `app/components/form/SearchField.tsx`. It is used by `HutangScreen`,
`RentalScreen`, `PilihKendaraanScreen`, and `HutangFormScreen`.

But **`UserScreen` and `PilihUserScreen` still hand-roll their own** search box — a local
`searchInputContainer` style plus an inline `<MaterialIcons name="search" />`
(`UserScreen.tsx:135–137`, `PilihUserScreen.tsx:188–190`). Three implementations of one control.

This is very likely *why* search feels visually inconsistent between tabs.

**Fix:** migrate both screens to `SearchField`. Delete the local `searchInputContainer` styles and
the inline search icons. Watch for behavioural differences — `PilihUserScreen` has an
`isSearchMode` state that the shared component may not account for; check before ripping.

> **Note — 2.1 and 2.3 are the same bug.** A shared component was introduced mid-project and the
> screens written *before* it were never migrated. The chevron is the visible symptom; `SearchField`
> is the invisible one. Fixing only the visible half guarantees a "minor UI" line item on the next
> release too.

### 2.4 `KendaraanScreen` — **not in this release**

25 lines, still on the pre-Stitch token system (`typography.heading`, `colors.text` — the only
screen that is), commented out of `MainNavigator` but still typed in `navigationTypes.ts`. Not
user-visible, so not a UI bug.

Logged in `docs/known-technical-debt.md` instead. It isn't a v1.0.2 problem; it's a "vehicle
management doesn't exist yet" problem.

## 4. Show the app version

- **Status:** open
- **Why:** so Farrel knows which JS bundle is actually running when something goes wrong, and mom
  has a number she can read out loud over the phone.

### ⚠️ Do not bump `version` in `app.json`

`app.json` still reads `"version": "1.0.0"` — v1.0.1 shipped as a pure OTA with no bump, on purpose.
The `runtimeVersion` policy is **`appVersion`**.

So bumping `version` to `1.0.2` would make OTA updates target runtime `1.0.2`, while mom's installed
APK is runtime `1.0.0` — **she would silently stop receiving updates.** `app.json` stays at `1.0.0`
until native deps change and a new APK ships.

The corollary: `Application.nativeApplicationVersion` would report **"1.0.0" forever**. It is the
wrong source for this feature.

### Design

**Source of truth — a JS constant, shipped with the bundle:**

```ts
// app/config/release.ts
export const RELEASE = "1.0.2"
```

Because it travels inside the OTA payload, it is always the truth about the bundle mom is running.

> **Free diagnostic:** if an OTA silently fails to apply, her screen still shows the *old* number.
> You would know immediately, without asking her to do anything.

**Underneath it, the actual update identity**, from `expo-updates` (already a dependency,
`~55.0.24`): `Updates.updateId` (short form) and `Updates.createdAt`. When she is running the
embedded APK bundle rather than an OTA, `updateId` is null — display **`bawaan`**.

**Placement — `BerandaScreen` scroll footer**, below the due-today list:

```
     Lavender Ops · v1.0.2
     pembaruan a1b2c3d · 12 Jul 2026     ← small, grey
```

Chosen because the version is needed *when something is already wrong* and you are on the phone
asking "what version are you on?" — so mom has to be able to **find it on demand, from a verbal
instruction**. "Scroll to the bottom of the home screen" works. The splash screen was rejected: it
flashes past in under a second and she cannot summon it back.

**Remember to bump `RELEASE` before publishing the OTA.** It is a hand-maintained constant; nothing
enforces it.

## 5. Extract `showToast` to a shared util

- **Status:** open
- **Source:** v1.0.2 audit, 2026-07-12

`showToast` is defined **six times**, byte-identical, as a local function:

| Screen | Line |
|---|---|
| `BerandaScreen.tsx` | 29 |
| `RentalDetailScreen.tsx` | 44 |
| `PengembalianScreen.tsx` | 45 |
| `DetailSewaScreen.tsx` | 46 |
| `PilihKendaraanScreen.tsx` | 26 |
| `PilihUserScreen.tsx` | 26 |

```ts
function showToast(msg: string) {
  if (Platform.OS === "android") {
    ToastAndroid.show(msg, ToastAndroid.SHORT)
  } else {
    // …
  }
}
```

**Fix:** move it to `app/utils/showToast.ts`, import it in all six screens, delete the local copies
(and the now-unused `Platform` / `ToastAndroid` imports where nothing else uses them).

A pure mechanical move — zero behaviour change, no rental-math surface. It is the one safely-fixable
piece of a much larger duplication problem (see the note below), and it stops the sixth copy from
becoming a seventh.

> ### ⚠️ The larger problem this is a symptom of — **deliberately NOT in v1.0.2**
>
> The audit found that the **Phase-0 shared form library is barely used.** `app/components/form/`
> contains `FieldCard`, `FuelGauge`, `SectionLabel`, `Stepper`, `RupiahInput` — all with passing
> tests. But `DetailSewaScreen` and `PengembalianScreen`, the two biggest files in the app (48KB and
> 50KB), **import only `PhotoRow`** and redefine everything else locally:
>
> | Helper | Local copies | Shared version exists? |
> |---|---|---|
> | `SectionLabel` | 3 | ✅ |
> | `FuelGauge` | 3 (one renamed `BensinGauge`) | ✅ |
> | `FieldCard` | 2 | ✅ |
> | `Stepper` | 2 | ✅ |
> | `parseRupiahInput` | 2 | ✅ (`RupiahInput`) |
> | `paymentMethodLabel` | 3 (one renamed `methodLabel`) | — |
> | `groupByFirstLetter` | 2 | — |
>
> This is the **parent** of items 2.1 (chevron) and 2.3 (`SearchField`) — the same drift, one level
> up. It also explains why those two files are 48–50KB.
>
> **It is out of scope here on purpose.** `DetailSewaScreen` is tariff composition;
> `PengembalianScreen` is fuel adjustment and auto-debt creation — the highest-risk code in the app,
> where `docs/02` §6 says the math must be correct. A "just swap in the shared component" refactor
> there is how a safe OTA becomes a silent money bug. The copies have **already diverged**:
> `DetailSewa`'s local `FuelGauge` takes `max = 8`; `Pengembalian`'s takes no `max` at all.
>
> Logged as `docs/known-technical-debt.md` #4. It needs its own release and its own tests.

## Implementation outcome — 2026-07-15

Implemented on branch `v1.0.2-polish-and-honesty` (commits `750bafb` → `7430fb9`), verified green
(compile clean, 22 suites / 89 tests), and **shipped OTA 2026-07-15** to the `preview` channel
(runtime `1.0.0`, update group `0ce732a0-9d6d-410b-b292-d4e1b498c908`). `eas update:list` confirmed the
update targets runtime `1.0.0` — mom receives it on her next app launch.

Two deviations from the spec above, both benign:

- **`showToast` migrated into 4 screens, not 6.** `BerandaScreen`'s copy was dead code (deleted, no
  import added); `PilihUserScreen`'s only call-site was the dead-end link, replaced by navigation in
  item 3a (so it also ends importless). The util is defined once in `app/utils/showToast.ts`.
- **`SearchField` needed two additive props first** (`onFocus`, `inputRef`) to preserve the
  search-mode/blur behaviour `UserScreen` and `PilihUserScreen` already had — an extension, not a
  behaviour-dropping swap. The four existing callers are unaffected.

Item **1 (text sizes)** remains **open and blocked** on mom's input — it ships nothing here and
carries forward to v1.0.3.

> **Note on the plan's Task 5 grep.** The plan's `rg inlineEditBtn app/ → expect empty` check was
> over-broad: `inlineEditBtn` is a style name independently defined in three screens.
> `RentalDetailScreen`'s dead "Edit" buttons and its `inlineEditBtn` style **are** deleted; the
> remaining matches in `DetailSewaScreen`/`PengembalianScreen` are pre-existing, **functional** edit
> affordances (change customer / change vehicle / edit return time), untouched by this release. No
> spec acceptance criterion is affected.
