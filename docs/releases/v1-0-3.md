# v1.0.3 — Edit an active rental

- **Status:** open — **not designed.** This document is a scoping note, not a spec.
- **Origin:** split out of v1.0.2 item 3 on 2026-07-12. The two "Akan segera tersedia" Edit buttons
  on `RentalDetailScreen` turned out to need a migration, an RPC, and a new connector — a real
  feature riding alongside four cosmetic fixes. It was pulled out so it could get its own design
  pass.
- **Prerequisite:** v1.0.2 ships first, having **removed** those two Edit buttons. v1.0.3 puts them
  back, working.

## The gap

**A rental is write-once.** `app/services/rentals/index.ts` exposes `createRental`, and after that
only `addPayment`, `closeRental`, and the payment edit/delete connectors. There is **no
`updateRental`**. Nothing in the app can amend a rental after it is created.

That is the whole problem. Mom photographs the wrong thing, sets the fuel gauge wrong, or needs to
add a note — and the record is frozen until return.

## Scope

### 3b. Edit Catatan Rental

`RentalDetailScreen.tsx:632` — the "Catatan Rental" section.

A plain text column. **No rental-math exposure**, no photos, no storage. This is the safe half and
the natural first task.

### 3c. Edit Kondisi Keluar

`RentalDetailScreen.tsx:365` — the "Kondisi Keluar" section: `KondisiSnapshot` (`bensinKotak` +
photos).

Harder, and **it touches money**:

> ⚠️ `kondisiKeluar.bensinKotak` is the **baseline the fuel adjustment compares against at return**
> (`docs/02` §6 — more fuel returned → reduce subtotal; less → add). Editing it retroactively
> changes what the customer owes.

- **Hard-gate to `status === "ACTIVE"`.** While the rental is out, the return calculation has not
  run, so amending the baseline is safe and correct. Once `COMPLETED`, the math is settled and an
  edit would silently invalidate a closed record — and possibly an auto-created Hutang. Do not allow
  it. (If a completed rental genuinely needs correction, that is an admin concern, and a separate
  design.)
- Photos need **replace / remove**, not just add — which means client-side storage deletion. See the
  v1.0.1 lesson below.
- Reuse `FuelGauge` and `PhotoRow` from `app/components/form/`.

## Known landmines (learned the hard way in v1.0.1 — read before designing)

1. **`SECURITY DEFINER` does not cover client-side steps.** The RPC bypasses RLS for what runs
   *inside* it. A photo deletion issued from the app is a separate, client-side call and is still an
   RLS subject. v1.0.1 shipped a hard-delete whose photo cleanup failed **silently** for exactly this
   reason, leaving customers' KTP/KTM scans in the bucket. Migration `0017` granted storage DELETE to
   the **admin role only** — so **mom's `ops` role still cannot delete any file.** If 3c lets mom
   replace an exit photo, she will need a storage DELETE path that does not exist yet. Design it
   deliberately; do not assume the RPC covers it.

2. **Supabase errors are not `Error` instances.** `supabase.rpc()` returns a plain object
   (`{message, details, hint, code}`). A connector doing `if (error) throw error` throws that, and any
   caller checking `e instanceof Error` gets `false` and discards the real Postgres message. Throw a
   real `Error`: `throw new Error(error.message)`. And **never mock a Supabase failure as
   `new Error(...)` in tests** — that shape does not exist, and this exact mock hid a real bug through
   two green reviews.

## Rough shape (unvalidated)

- Migration `00XX_update_rental` — `rpc_update_rental_catatan`, `rpc_update_rental_kondisi_keluar`
  (or one RPC with a payload; decide at design time). `SECURITY DEFINER`, ACTIVE-gated, audited.
- Connector `updateRental(rentalId, input): Promise<Rental>` — locked signature once written
  (`docs/02` §3).
- `RentalDetailScreen`: restore the two Edit affordances; edit UI for notes (text) and kondisi
  (`FuelGauge` + `PhotoRow`).

## Before implementing

Run `superpowers:brainstorming` on this. The scoping above is not a design — in particular the
storage-permission question in landmine #1 is unresolved and could change the whole shape of 3c.

Also consider having `rental-math-reviewer` look at 3c specifically. It is the first thing since
v1.0.0 to move a number the tariff/fuel calculation depends on.
