### Ride-along: offline-save timeout (debt #5)

In scope: a timeout / abort wrapper on the Supabase client's `fetch` so a save that can't reach the
server **fails with a clear message** instead of hanging silently, plus the UI decision for what the
user sees when it fires. That is the whole of #5 for this release.

- **Why bundled, not deferred:** it completes **PRD-1 BR-7** (safe save — "a failed save shows the real
  error and keeps Mom in edit mode to retry") for the **offline** case. Without a timeout an offline
  save never fails, so BR-7 is unreachable in the field exactly where Mom uses this feature.
- **Blast-radius guard (why this needed a deliberate call):** the fix changes error behaviour in
  **every connector at once**, not just the new one. Confine it to `app/services/supabase/client.ts`
  plus the on-timeout UI; it **MUST NOT** alter any logic in the rental-math screens
  (`DetailSewaScreen` / `PengembalianScreen`) — PRD-1 touches those for UI only. The tester must
  confirm no regression on existing connectors' happy paths (a successful call is unchanged).
- **Not bundled — debt #1** (the ~24 raw-postgrest-error throws). The register suggests pairing #1 with
  #5 since both change client-wide error behaviour, but this release takes **#5 only**. PRD-1's new
  connector still throws a real `Error(message)` by its own constraint; the other ~24 sites stay deferred.
- **HOW is owed to the plan:** the existing implementation plan covers **PRD-1 only**. #5's timeout
  mechanism and on-timeout UX are a **Lead/dev** call — add them to
  `docs/superpowers/plans/2026-07-15-v1-0-3-edit-active-rental.md` (or a sibling plan) before dispatch.

## Rollback

> ⚠️ **Rewritten 2026-07-21.** The previous text said an OTA republish alone was a safe rollback
> because the migration was additive and inert. That was true when this release shipped **one**
> migration. It shipped **three**, and two of them modify functions Mom uses every day.
> **An OTA republish does NOT undo them.**

v1.0.3 applied three migrations (`db push`, 2026-07-21):

| Migration | Revertible by OTA? |
|---|---|
| `20260720073455_rpc_update_rental` | **Yes, effectively.** Additive `SECURITY DEFINER` RPC, no schema/column change. Republish the prior JS and nothing calls it — an unused RPC is inert. |
| `20260720103317_rpc_auth_gate_hardening` | **No.** Rewrites the guard line of 10 shipped RPCs and `REVOKE`s `EXECUTE` from `PUBLIC`/`anon`. Server-side the instant the push lands. |
| `20260721150806_close_rental_exclude_deleted_payments` | **No.** Changes how `rpc_close_rental` computes `total_paid`, and therefore the size of every auto-created hutang. |

**So there are two different failure modes, with two different responses.**

**1. A JS/UI defect** (the edit screen misbehaves, a bad toast, a broken layout) — OTA-republish the
prior update group. The #5 fetch-timeout is JS-only and reverts the same way. Nothing server-side to
undo. This is the ordinary case.

**2. Mom is locked out** (she cannot create / close a rental, record a payment, or load the dashboard) —
this is a **privilege** failure and OTA cannot touch it. Apply:

```powershell
cd apps/lavender-ops-mobile
npx supabase db query --linked -f supabase/ROLLBACK_restore_rpc_grants.sql
```

Read that file's header before running it — it deliberately does **not** re-open
`recompute_rental_hutang`, and it does **not** cover `rpc_update_rental` (that path is new in v1.0.3,
so losing it degrades a new feature rather than taking away something Mom had before).

**3. A guard-polarity failure** (a guard that now *always* raises, so Mom is rejected by the function's
own logic rather than by privileges) — **neither** OTA nor the grants rollback fixes this. Restoring
`PUBLIC` changes who may call the function, not what it decides once called. This needs a **forward
migration** correcting the guard.

**Reverting the money fix** (`20260721150806`) is possible but should be a deliberate decision, not a
reflex: reverting re-introduces a bug that silently under-records customer debt. Do it only with a
forward migration, never by editing the applied file.

### Notable near-misses (preserved deliberately)

- **A verification script that would have passed vacuously.** Its REVOKE section cleared JWT *claims*
  but not the *session role*, and ran as an elevated role holding `EXECUTE` regardless. Worse, nothing
  would have caught a broken `authenticated` grant — which kills the app for every real user. Fixed
  with `has_function_privilege` on **both** roles.
- **The rollback would have undone itself.** `db push` applies every pending migration in one shot with
  no per-file selection, so a rollback living in `migrations/` would have been applied by the very push
  that shipped the hardening. It lives at `supabase/ROLLBACK_restore_rpc_grants.sql` instead.
- **Three functions never had *any* explicit `GRANT`** (`rpc_get_dashboard_summary`, `rpc_create_rental`,
  `rpc_close_rental`) — they ran purely on the default `PUBLIC` grant. A `REVOKE` alone would have
  locked out every user on push.
- **A body-invariance test that passed a reordering.** The guard test for the `deleted_at` fix first
  used a set-difference diff, which is order-blind — hoisting a statement changes the money and
  produced an empty diff. Rewritten index-aligned and then verified non-vacuous by mutation (reverting
  the auth guard fails 2 tests, a pure reorder fails 1, dropping the filter fails 3).
